# Chapter 4: Advanced Techniques for Text Generation with LangChain

## Core Idea
Single prompts break down on three kinds of problems: content larger than the context window, tasks that need several LLM inputs and outputs combined in sequence, and complex reasoning or agentic work. LangChain handles these with composable runnables (templates, parsers, evaluators, loaders, splitters, chains) joined by LCEL's `|` pipe. Most of the chapter applies **Divide Labor**, **Specify Format**, and **Evaluate Quality**.

> API note: the code is from the 2024 edition (`langchain_openai`, `langchain_core`, `pydantic.v1`, `load_summarize_chain`, `create_extraction_chain_pydantic`, `gpt-3.5-turbo-1106`). Several of these imports and helpers have since been moved or deprecated. Learn the patterns from it and check the current API before reusing the code.

## Frameworks Introduced
- **LangChain Expression Language (LCEL)**: `chain = prompt | model | output_parser`. The pipe works like a Unix pipe: each runnable's output becomes the next one's input.
  - When to use: any multi-step LLM pipeline (formatting a prompt, calling the model, parsing the result, post-processing).
  - How: compose runnables left to right, then call `.invoke()`, `.batch()`, or `.stream()` (async versions are prefixed with `a`: `.ainvoke()`, `.abatch()`). Order matters, so `model | prompt` fails at invoke time. The **first element must be a runnable**: a plain dict like `{"age": 18}` errors, but `{"age": itemgetter("age")}`, `RunnableLambda(...)`, `RunnablePassthrough()`, or `RunnableParallel(...)` all work.
  - Why it works / failure mode: every step shares one interface, so you can swap models, parsers, or functions without rewriting glue code. The usual failure is a downstream template placeholder that receives no value. Carry keys forward explicitly with `itemgetter`.
- **Output Parsers**: an abstraction that turns raw LLM strings into structured types. It replaces the regex parsing from Ch 3.
  - When to use: whenever downstream code consumes LLM output.
  - How: (1) put `parser.get_format_instructions()` into the prompt, and (2) call `parser.parse(llm_output)` or add the parser to the end of the LCEL chain. Available types: List, Datetime, Enum, Auto-fixing (if the wrapped parser fails, another LLM call fixes the output), Pydantic (JSON), Retry, Structured, XML. The authors prefer the **Pydantic (JSON) parser** with `ChatOpenAI` because it is the most flexible.
  - Principle(s): Specify Format.
  - Failure mode: LLMs don't always follow the format, so wrap calls in `try/except`, return a default object (fields set to `None`) on failure, and count those as errors in evals.
- **LangChain Evals**: score prompt and model outputs against test cases (input/output pairs with known answers). The ground truth can be curated by hand or generated by a smarter model such as GPT-4.
  - When to use: before a prompt change or a switch to a cheaper or open-source model, to show quality holds.
  - How: (1) generate reference labels with GPT-4. (2) Run the candidate models (e.g. GPT-3.5-turbo, Mixtral 8x7b as `mistral-small`). (3) Score them with an evaluator. Exact string match gives 1/0. String distance (Levenshtein) and embedding distance allow fuzzy or semantic matches. `labeled_pairwise_string` has GPT-4 pick between two outputs and explain why. Log results to LangSmith or Weights & Biases.
  - Principle(s): Evaluate Quality.
  - Caveat: if GPT-4 is bad at a task, it may also be bad at evaluating that task, so manually review the evaluator's reasoning.
- **OpenAI Function Calling**: an alternative to output parsers. Fine-tuned models decide when a function should run and return JSON containing the function name and arguments.
  - When to use: chatbots that take actions (`schedule_meeting`), turning natural language into API calls ("Turn on the hallway lights" → `control_device`), and structured extraction.
  - How: (1) define the Python function and a name→function map. (2) Write a JSON schema with name, description, parameters, and required fields. (3) Pass it as `tools=`. (4) If `response.tool_calls` is set, `json.loads` the arguments and run the function. (5) Append the result as a `"function"` role message. (6) Call the model again to get a user-friendly reply. `tool_choice`: `"auto"` (default; the model decides), `"none"` (no function call), or `{"type":"function","function":{"name":...}}` (forces a specific function).
  - Principle(s): Specify Format. A detailed schema with name and description is the model's blueprint.
- **Parallel Function Calling**: a single user message with several intents produces several `tool_calls`. Loop over them, run each one, and append each result.
- **Function Calling in LangChain**: describe the schema as a Pydantic model instead of writing JSON. Use `convert_to_openai_tool(p)`, then `model.bind_tools(tools)`, then `prompt | model | PydanticToolsParser(tools=schemas)`. Shortcut: `create_extraction_chain_pydantic(Person, model)` returns a list with one object per entity found.
- **Query Planning**: parse a multi-intent query into a **query graph** of sub-queries, each with an `id`, a `question`, and `dependencies: List[int]`. A Pydantic `QueryPlan` holds the graph and a `PydanticOutputParser` produces it.
  - When to use: user queries with several intents and complex dependencies (e.g. get top customers → average their age → email John, while separately welcoming Sarah).
- **Few-Shot Prompt Templates**: two ways to inject k-shot examples.
  - Fixed-length: put `examples` (a list of dicts) and an `example_prompt` (a human/ai message pair) into a `FewShotChatMessagePromptTemplate`, then embed that between the system message and the human message of a `ChatPromptTemplate`.
  - Example selector: `LengthBasedExampleSelector(examples, example_prompt, max_length, get_text_length)` drops examples as the user input gets longer so the context window isn't exceeded. Replace the default word-split length function with a tiktoken counter so `max_length` is measured in tokens.
  - Principle(s): Provide Examples and Specify Format.
- **Data Connection pipeline**: Sources → **Document loaders** (PDF, DOCX, CSV, web; `PyPDFLoader`, `Docx2txtLoader`, `CSVLoader`) → **Document transformers / text splitters** → **text embedding models** → **vector stores** → **retrievers**. Unstructured data goes through load, transform, embed, and store in a vector DB. For structured SQL/NoSQL/graph data, use an agent to run intermediate queries. Add a `metadata` dict to each `Document` (e.g. `description`, `source`).
- **Text Splitters**: split by token count, character count, recursively by multiple characters, code, or Markdown headers.
  - `CharacterTextSplitter.from_tiktoken_encoder(chunk_size, chunk_overlap, separator)` splits by tokens.
  - `TokenTextSplitter(chunk_size=500, chunk_overlap=50)` is passed into `loader.load_and_split(text_splitter=...)`.
  - **Recursive character splitting** (`RecursiveCharacterTextSplitter`) tries the delimiters `"\n\n"`, `"\n"`, `" "`, `""` in order and only moves to the next one if a chunk is still too large. This keeps paragraphs, then sentences, then words intact. `length_function` can be swapped for a token counter.
  - `.split_text()` returns strings, `.create_documents(texts, metadatas=[...])` returns Documents, and `.split_documents(docs)` re-splits Documents that are too long.
- **Task Decomposition**: break complex problems into manageable subproblems. This lowers cognitive load, isolates problems, and follows the single-responsibility principle. Uses: complex problem solving (legal case → context, laws, precedents, arguments), content generation (outline → sections → refine), large document summaries, conversational agents, and tutoring systems.
  - Principle(s): Divide Labor.
- **Prompt Chaining / Sequential Chain**: combine several tailored prompts, where each step's output becomes the next step's input (characters → plot → scenes → per-scene scripts).
  - How: build sub-chains (`prompt | model | StrOutputParser()`) and connect them with `RunnableParallel` and `itemgetter` so earlier keys flow down to later templates. For continuity, feed a **summary of the previous scene** into the next generation step. This acts as a simple buffer memory.
  - Principle(s): Divide Labor. A benefit: each step can use a different model, e.g. **a smart model for ideation and a cheap model for generation**, or a fine-tuned model per step.
  - Trade-off: sequential chains are slow, so use them for server-side or batch jobs, not real-time UX.
- **Document Chains** (for text that doesn't fit in one context window): **Stuff**, **Refine**, **Map Reduce**, and **Map Re-rank**. Select one with `load_summarize_chain(llm=model, chain_type="map_reduce" | "refine" | ...)`. See the table below.

## Key Concepts
- **Six LangChain modules**: Model I/O, Retrieval, Chains (runnables), Agents, Memory, Callbacks.
- **Message types**: `SystemMessage` (instructions, which GPT-4 weighs heavily, so put direction there), `HumanMessage`, and `AIMessage` (every chat model output is one).
- **Streaming**: `chat.stream(messages)` yields chunks as they are generated. This cuts perceived latency but makes it hard to parse output mid-stream.
- **`.batch()` / `RunnableConfig(max_concurrency=5)`**: run several generations in parallel requests, with a concurrency cap.
- **Prompt templates**: compared with f-strings, they add input validation, composition, k-shot example selectors, save/load to `.json`/`.yml`, and custom logic.
- **`PromptTemplate.save()` / `load_prompt()`**: store prompts as files so they can be shared and versioned. Not every template type supports this; fall back to pickle or `.txt`.
- **`RunnablePassthrough`**: passes its input through unchanged. **`RunnableLambda`** / `lambda` transforms dict values. **`RunnableParallel`** is interchangeable with a dict of runnables.
- **`itemgetter`**: pulls a key out of the previous step's dict so downstream placeholders always have values.
- **`StrOutputParser()`**: converts the chat model's `AIMessage` into a plain string. Use it at the end of most text chains.
- **Context length**: the maximum number of tokens one request can process. Chunks that are too large exceed it, and chunks that are too small lose context.
- **Chunk overlap**: tokens shared between neighbouring chunks. More overlap produces more chunks (in the example, 3 chunks became 6).

## Mental Models
- Think of **LCEL as Unix pipes for LLM calls**. If a stage is missing a key, the stage after it fails.
- Use **output parsers or function calling** whenever another program will read the LLM's response. A JSON response effectively turns the LLM into a flexible API.
- Use **evals with GPT-4 as the reference** to justify moving a task to a cheaper, faster, or self-hostable model (e.g. Mixtral). Test with an external API before you go to the trouble of self-hosting.
- There isn't a perfect document (chunk) size. Start from good heuristics, then build a train/test set and tune with evals.

## Anti-patterns
- **Hardcoding API keys** in scripts: a security risk. Use environment variables or a `.env` file loaded with python-dotenv.
- **Plain dict as the first LCEL element**: `{"film_required_age": 18} | prompt` errors because it isn't a runnable.
- **Too many few-shot examples**: the model overfits to the examples instead of following the prompt, and the examples use up tokens the response needs. Fixes: rephrase the prompt, tell the model to use the examples for format only, or fine-tune.
- **Trusting an LLM judge blindly**: a model that is weak at a task is weak at grading it too.
- **Regex parsing of free text** when an output parser or function call would enforce structure.
- **Sequential chains in real-time paths**: they add latency, so keep them server-side.
- **Vague function schemas**: the model can hallucinate parameters. Be explicit in the schema description and the system message.

## Code Examples
```python
# Pydantic output parser in an LCEL chain
class BusinessName(BaseModel):
    name: str = Field(description="The name of the business")
    rating_score: float = Field(description='''The rating score of the
    business. 0 is the worst, 10 is the best.''')

class BusinessNames(BaseModel):
    names: List[BusinessName] = Field(description='''A list
    of busines names''')

parser = PydanticOutputParser(pydantic_object=BusinessNames)
chain = chat_prompt | model | parser
result = chain.invoke({
    "principles": principles,
    "industry": "Data Science",
    "format_instructions": parser.get_format_instructions(),
})
```
- **What it demonstrates**: Specify Format end to end. Format instructions go into the prompt, and the chain returns typed Python objects.

```python
# Sequential chain: carry keys forward with RunnableParallel + itemgetter
master_chain = (
    {"characters": character_generation_chain, "genre": RunnablePassthrough()}
    | RunnableParallel(
        characters=itemgetter("characters"),
        genre=itemgetter("genre"),
        plot=plot_generation_chain,
    )
    | RunnableParallel(
        characters=itemgetter("characters"),
        genre=itemgetter("genre"),
        plot=itemgetter("plot"),
        scenes=scene_generation_plot_chain,
    )
)
story_result = master_chain.invoke({"genre": "Fantasy"})
```
- **What it demonstrates**: Divide Labor through prompt chaining. Each stage adds a key, and all earlier keys are passed along.

```python
# Map-reduce summarization over text too long for one context window
text_splitter = CharacterTextSplitter.from_tiktoken_encoder(

docs = text_splitter.create_documents([all_character_script_text])
```

## Reference Tables

**Document chain strategies (Table 4-1)**

| Approach | How it works | Advantages | Disadvantages |
|---|---|---|---|
| Stuff | Inserts all documents into a single request | Simple; ideal for small documents and few inputs | Breaks on large or many documents (prompt size limit) |
| Refine | Loops over the documents, updating the running output with each one | Iterative refinement; control at each step; good for progressive extraction | Slow loop; poor fit for real-time |
| Map Reduce | Map: run an LLM on each document. Reduce: combine the results (with optional recursive compression) | Each document handled independently; scales to large datasets | Needs careful management; compression adds complexity and **loses document order** |
| Map Re-rank | Runs the prompt on each document and scores confidence; returns the highest-scoring answer | Confidence score for each answer helps pick the best one | Ranking is complex; unreliable if scoring is poorly tuned |

**Function-calling `tool_choice`**

| Value | Behaviour |
|---|---|
| `"auto"` (default) | Model decides whether to call a function and which one |
| `"none"` | No function call |
| `{"type":"function","function":{"name":"my_function"}}` | Forces that function |

## Worked Example
**Evaluating a cheaper model on transaction classification**
1. GPT-4 labels a dataframe of bank transaction descriptions with `transaction_type` (Purchase/Withdrawal/Deposit/Bill Payment/Refund) and `transaction_category` (Food/Entertainment/Transport/Utilities/Rent/Other). These labels are the ground truth.
2. The Pydantic model `EnrichedTransactionInformation` constrains both fields with `Literal[...]` or `None`.
3. Chain: `prompt | ChatMistralAI("mistral-small") | StrOutputParser() | remove_back_slashes | output_parser`. The plain function strips the stray backslashes Mistral tends to emit in JSON keys before the Pydantic parse.
4. Loop over the rows. On an exception, store an object with `None` fields so the batch keeps going and the failure counts as an error.
5. Exact-match scoring gives Mistral **77.5% accuracy**.
6. Rerun the task with `gpt-3.5-turbo-1106` in JSON mode, then compare the two with `load_evaluator("labeled_pairwise_string").evaluate_string_pairs(prediction=gpt35, prediction_b=mistral, input=..., reference=...)`. On the first row, GPT-4 reasons that the two outputs are identical and correct, and returns `[[C]]` (tie) with score 0.5.

The result tells you whether the cheaper or open-source model is good enough to save cost and latency, or to keep data in-house.

## Key Takeaways
1. Use LCEL (`prompt | model | parser`) as the default way to build multi-step LLM pipelines. Start every chain with a runnable and pass keys forward with `itemgetter`/`RunnableParallel`.
2. Get structure through output parsers (Pydantic is the most flexible) or through function calling. Either way, handle parse failures explicitly.
3. Measure before and after any change. GPT-4-generated references plus exact-match, distance, or pairwise evaluators let you move work to cheaper models with evidence.
4. Use few-shot templates for examples, and use `LengthBasedExampleSelector` (counted in tokens) when input length varies.
5. To bring in your own data: load it into `Document`s, add metadata, and split with token- or recursive-character splitters. Tune chunk size and overlap with evals.
6. Decompose big tasks into a chain of prompts, which allows a different model per step and summary-based memory between steps. Keep these chains off latency-critical paths.
7. For text longer than the context window, pick a document chain: Stuff for small inputs, Refine for progressive extraction, Map Reduce for scale, Map Re-rank for the most confident answer.
