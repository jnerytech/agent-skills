# Chapter 8: Dataset Engineering

## Core Idea
The quality of a model is bounded by the quality of its training data; dataset engineering is the discipline of deliberately curating, synthesizing, and processing data so a model learns exactly the behaviors you want, within budget. It is mostly toil — and the hardest steps (annotation guidelines, verification, deciding what data you need) resist automation.

## Frameworks Introduced
- **Three criteria of data curation (quality, coverage, quantity)**: every dataset, across every training phase, is judged on these three axes. Cooking analogy: quality = ingredient freshness, coverage = right mix of ingredients, quantity = how much.
  - When to use: as the master checklist whenever you build or audit a training set.
  - How: ensure data is high-quality (6 traits below), covers the diversity of expected usage, and is large enough for your finetuning method/task/base-model.
- **Six characteristics of high-quality data**: relevant, aligned with task requirements, consistent, correctly formatted, sufficiently unique, compliant.
  - When to use: defining "good" before annotating or filtering.
  - How: write per-trait acceptance rules into your annotation guideline; "aligned" (not "accurate") because the desired output depends on the task.
- **Data quantity sizing rule**: amount needed depends on finetuning technique, task complexity, base-model performance (plus quality/diversity).
  - When to use: deciding how many examples to acquire/annotate.
  - How: small data + advanced model → PEFT/LoRA; large data → full finetuning on smaller models. Start with ~50 examples, plot the performance-gain curve over 25/50/100% subsets to extrapolate need.
- **Data flywheel**: a loop where data generated by your users continuously improves the product, which attracts more users/data.
  - When to use: as the strategic goal of data acquisition — application data is the highest-value source (perfectly distribution-matched).
  - How: capture user content, system-generated usage data, and user feedback (see Ch 10).
- **Data synthesis taxonomy**: rule-based/templates → simulation → AI-powered. Reasons to synthesize: increase quantity, coverage, quality; mitigate privacy; distill models.
  - When to use: when real data is scarce, sensitive, or humans are a quality bottleneck.
  - How: pick the cheapest technique that yields *verifiable* data; mix synthetic with real to avoid collapse.

## Key Concepts
- **Data-centric vs model-centric AI**: improving performance by enhancing data vs enhancing architecture/training.
- **Data augmentation**: new data *derived* from real data (flip a cat image, synonym swap).
- **Data synthesis**: data that *mimics* real properties but isn't real (simulated bot movements, synthetic patient records).
- **Reverse instruction**: take high-quality long content, use AI to generate the prompt that would elicit it — avoids hallucinated responses.
- **Back-translation**: translate output back to source and compare to original to verify quality (used for translations and code↔docs).
- **Self-play**: a model generates training data by playing against itself (AlphaGo, OpenAI Dota 2).
- **Ossification**: pre-training can freeze weights so they resist finetuning; worse for smaller models and large finetuning sets.
- **Model collapse**: recursive training on AI-generated data causes irreversible degradation; rare events vanish over iterations.
- **Data verification**: checking data quality via functional correctness, AI judges, heuristics, or anomaly detection.
- **Deduplication**: removing whole-document / intra-document / cross-document duplicates that skew distribution and contaminate test sets.
- **Data lineage**: provenance of data; AI generation obscures it, risking copyright/contamination leakage.

## Mental Models
- **Data as ingredients, training as cooking**: quality, coverage (mix), quantity. Spoiled ingredients ruin the dish regardless of compute.
- **Curation is addition AND subtraction**: you add data to teach behaviors and *remove* data to make a model unlearn bad ones (e.g., unsolicited rewrites).
- **You synthesize what you can verify**: like evaluation-driven development — coding dominates synthetic data because code execution gives free ground truth.
- **Diminishing returns curve**: each additional batch of examples gives less lift; diversity of *tasks* (9→282 tasks mattered) often beats raw volume.

## Anti-patterns
- **Abandoning annotation guidelines halfway**: hoping the model "figures it out" — guidelines are the hardest, most valuable part (LinkedIn's experience).
- **Training on 100% synthetic / recursively self-generated data**: causes model collapse; always mix with real data and verify.
- **Indiscriminate distillation (superficial imitation)**: student mimics teacher's *style*, learns to produce answer-shaped hallucinations it can't actually derive; fix base models for reasoning, not imitation.
- **Editing data in place**: a script bug corrupts your only copy — keep originals.
- **Prompt/format mismatch at inference**: finetuned on `"burger -->"` but querying `"Item: burger"` causes silent failures.
- **Ignoring AI-judge position bias**: first-position preference; ask twice with swapped order, keep only consistent verdicts (NVIDIA).

## Worked Example
**Llama 3 synthetic coding pipeline** (2.7M examples generated). (1) AI generates diverse programming problem descriptions. (2) AI generates solutions per language, with good-programming rules + CoT. (3) Verification: run through parsers/linters (syntax), AI-generated unit tests (runtime); on failure, re-prompt with the problem + faulty code + tool feedback. Only fully-passing examples are kept. (4) AI translates passing code to other languages — drop translations that fail tests. (5) AI generates explanations/docs, then back-translates docs→code; keep only if regenerated code is faithful. Result: every example is *programmatically verifiable*, embodying "synthesize what you can verify."

## Key Takeaways
1. A small amount of high-quality data beats a large amount of noisy data (Yi: 10K > 100Ks; LIMA: 1,000 prompts rival GPT-4 in 43% of cases).
2. The three criteria — quality, coverage, quantity — apply across all training phases, but the optimal data *mix* differs per phase.
3. Match data volume to your method/task/base-model: small data → PEFT on strong models; large data → full finetuning on smaller models.
4. Start small (~50 examples) and plot the performance-gain curve before investing in large-scale annotation.
5. Synthetic data scales quantity/coverage/quality and protects privacy, but only verified synthetic data improves models — and pure-synthetic recursion collapses them.
6. The data flywheel (your own application data) is the highest-value, best-distributed source you can have.
7. Manual data inspection has the highest value-to-prestige ratio in ML — 15 minutes of staring at data saves hours.
