# Glossary — Accelerate (Forsgren, Humble, Kim, 2018)

**24 capabilities** — Capabilities that statistically drive software delivery performance, in 5 categories: CD (8), architecture (2), product & process (4), Lean management & monitoring (5), culture (5) (Ch 1, 17)
**Batch size** — Work moved through delivery at once; proxied by deployment frequency (Ch 2)
**Burnout** — Exhaustion from overwork/stress felt as helplessness; reduced by CD, Lean management, generative culture (Ch 9)
**Capabilities model** — Outcome-based, multidimensional, never-"done" improvement approach; preferred over maturity models (Ch 1)
**Catchball** — Two-way routing of problems and learning across levels (Ch 16)
**Change advisory board (CAB)** — External approval body; negatively correlated with tempo, no gain in stability (Ch 1, 7)
**Change fail rate** — % of production changes that degrade service or need remediation (Ch 2)
**Cluster analysis** — Unsupervised grouping that yields high/medium/low performers (Ch 2, 12, 17)
**Continuous delivery** — Capabilities to get any change into production safely, quickly, sustainably (Ch 4)
**Continuous integration** — Short-lived branches merged to trunk frequently; each change built and tested (Ch 4)
**Convergent / discriminant validity** — Related items correlate / unrelated items don't (Ch 3, 13)
**Cronbach's alpha / composite reliability** — Internal-consistency tests; ≥ 0.70 (Ch 13, 17)
**Cross-sectional design** — Data collected at one point in time (Ch 1, 15)
**Deployability / testability** — Release independently / test without an integrated environment (Ch 5)
**Deployment frequency** — How often code reaches production (Ch 2)
**Deployment pain** — Fear and anxiety around deploying; a tell of poor delivery practices (Ch 4, 9)
**eNPS** — Employee Net Promoter Score: % promoters (9–10) − % detractors (0–6) (Ch 10)
**Faux Agile** — Agile rituals without changing culture or processes (Ch 8)
**Fuzzy front end** — High-variability design part of lead time; excluded from the metric (Ch 2)
**Generative culture** — Westrum's performance-oriented culture: high cooperation, messengers trained, failure → inquiry (Ch 3)
**Hoshin Kanri** — Lean strategy deployment linking strategy to front line (Ch 16)
**Identity** — Employees identifying with org values/goals (Ch 10)
**Inferential prediction** — Theory-driven predictive analysis used when experiments aren't possible; what "drives" means in the book (Ch 12, 17)
**Inverse Conway Maneuver** — Restructure teams to get the architecture you want (Ch 5)
**J-curve** — Medium performers temporarily do more manual work/rework than low performers (Ch 17)
**Latent construct** — Unobservable concept measured via several survey items (Ch 13)
**Lead time for changes** — Code committed → code running in production (Ch 2)
**Lean management** — WIP limits + visual displays + monitoring feedback for decisions (Ch 7)
**Lean product management** — Small batches, visible flow, customer feedback, team experimentation (Ch 8)
**Lightweight change approval** — Peer review + deployment pipeline instead of CAB (Ch 7)
**Likert-type scale** — 1–7 agreement scale for survey items (Ch 3, 12)
**Loosely coupled architecture** — Teams change, test and deploy independently; biggest CD contributor in 2017 (Ch 5)
**Maturity model** — Linear, static levels; encourages declaring transformation "done" (Ch 1)
**Obeya** — Visual management room for objectives, gaps and problems (Ch 16)
**Organizational performance** — Profitability, productivity, market share (and noncommercial goals) (Ch 2)
**Outcomes vs. output** — Measure results, not activity (lines of code, velocity, utilization) (Ch 2)
**PDCA** — Plan–Do–Check–Act learning cycle (Ch 16)
**Psychometrics** — Science of measuring constructs via surveys (Ch 13)
**Rugged DevOps / DevSecOps** — Security integrated into DevOps (Ch 6)
**Shift left on security** — Infosec built into design and daily delivery work (Ch 4, 6)
**Small batches** — Work completable in under a week; MVPs (Ch 8)
**Snowball sampling** — Respondents recruit peers (Ch 1, 15)
**Software delivery performance** — Construct of lead time, deployment frequency, time to restore (change fail rate correlated but separate) (Ch 2, 3)
**Squad / Tribe / Chapter** — ING's cross-functional team / value-stream unit / discipline guild (Ch 16)
**Stability / Tempo** — Time to restore + change fail rate / lead time + deployment frequency (Ch 1, 2)
**Team experimentation** — Teams change specs without outside approval (Ch 8)
**Test data management** — Adequate test data on demand, not limiting tests (Ch 4)
**Time to restore service** — Time to recover from unplanned outage or impairment (Ch 2)
**Transformational leadership** — Vision, inspirational communication, intellectual stimulation, supportive leadership, personal recognition (Ch 11)
**Trunk-based development** — < 3 active branches, merged within a day, no code freezes (Ch 4)
**Unplanned work / rework** — Break/fix work; quality proxy (21% high vs 27% low performers) (Ch 4, 17)
**Utilization** — As it approaches 100%, lead time approaches infinity (Ch 2)
**Virtuous cycle** — Delivery performance and Lean product practices reinforce each other (Ch 8, 10)
**Wall of confusion** — Dev rewarded for throughput, ops for stability → conflict (Ch 2)
**Westrum typology** — Pathological (power), bureaucratic (rule), generative (performance) cultures (Ch 3)
**WIP limits** — Caps on work in progress to expose flow obstacles (Ch 7)
