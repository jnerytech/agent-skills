# Glossary — Docs for Developers

**Accessible (functional quality)** — content readers can reach and understand: their language, ~10th-grade reading level, alt text, captions (Ch 9).

**Accurate (functional quality)** — content is correct, current, with working samples (Ch 9).

**Alt text** — text alternative for an image so screen readers can convey it; better still, describe the image in body text (Ch 6).

**Anti-pattern** — a common practice that fails users (e.g. write-once docs, FAQ sprawl).

**Box-and-arrow diagram** — depicts data flow/relationships between entities (Ch 6).

**Callout** — Warning / Caution / Note block highlighting must-not-miss info out of the main flow (Ch 3).

**Card sorting** — writing each page on a card and rearranging to design information architecture (Ch 10).

**Changelog** — terse chronological record of changes; can be automated (Ch 2).

**Clear / Concise / Consistent (3 Cs)** — the components of structural quality (Ch 9); also the editing clarity goal (Ch 4).

**Code comments** — basic content type documenting *why* (decisions/trade-offs), not just *what* (Ch 2).

**Complete (functional quality)** — all prerequisites, tasks, and next steps present (Ch 9).

**Conceptual documentation** — explains ideas/how-it-works; no implementation detail; one concept per doc (Ch 2).

**Content gap** — requested information that doesn't yet exist (Ch 10).

**Content outline** — list of page titles, each with content type and one-line description (Ch 2).

**Content release process** — plan for publishing: when, who, where, what tools, how to announce (Ch 7).

**Content type** — reusable documentation pattern (code comments, README, getting started, conceptual, procedural, reference) (Ch 2).

**CSAT** — customer satisfaction score derived from surveys (Ch 8).

**Curse of knowledge** — bias of assuming others know what you know; the book's central obstacle (Ch 1).

**Deprecation** — marking content/features as no longer recommended, with notice before deletion (Ch 11).

**Diátaxis** — framework structuring docs into tutorials/how-to/reference/explanation (Appendix B).

**Document owner** — person explicitly responsible for a doc's upkeep (e.g. CODEOWNERS) (Ch 11).

**Document sentiment** — how readers feel about a page (yes/no "was this helpful?") (Ch 8).

**Documentarian** — documentation specialist/technical writer (Appendix A).

**Documentation plan** — flexible outline mapping the user journey across the content to write (Ch 2).

**Editing passes** — focused review rounds: technical accuracy → completeness → structure → clarity & brevity (Ch 4).

**Escape hatch** — cue (link/callout/note) signaling a user is in the wrong place and pointing elsewhere (Ch 2, Ch 10).

**Executable code sample** — runnable, copy-paste-and-personalize (Ch 5).

**Explanatory code sample** — not meant to run; output/block to learn from or compare (Ch 5).

**F-pattern** — the shape in which readers skim a page (Ch 3).

**Findable (functional quality)** — readers can navigate to and *through* content (Ch 9, Ch 10).

**Flow of information** — ordering content to match reader knowledge/expectations (Ch 3).

**Flowchart** — diagram of a process start→finish (rectangle=process, diamond=decision) (Ch 6).

**Freshness check** — last-modified date + timed owner review reminder (Ch 11).

**Friction log** — journal of using your own software as a user, logging expected vs. actual (Ch 1).

**Functional quality** — whether a doc accomplishes its purpose; more important than structural (Ch 9).

**Getting started documentation** — first-time experience; quickest path to a working integration (Ch 2).

**Hierarchy** — parent/child content structure, broad→specific (Ch 10).

**How-to guide** — procedural content solving a real business problem with real code (Ch 2).

**Information architecture (IA)** — the organizational structure of a doc set (Ch 10).

**Landing page** — short scannable page routing users to the right content (Ch 10).

**Linter (prose)** — tool flagging style/grammar/template/exclusionary issues; custom dictionaries (Ch 11).

**Migration guide** — helps users move off a deprecated feature; publish before announcing (Ch 11).

**Navigation cues** — breadcrumbs, side nav, labels, prereqs/next steps, escape hatches (Ch 10).

**Needs vs. wants** — document what users need, not what they say they want (Ch 1).

**Plussing** — Pixar rule: only criticize an idea if you also add a constructive suggestion (Ch 4).

**Procedural documentation** — tutorials and how-to guides; one action per step (Ch 2).

**Reference documentation** — cause-and-effect content: API reference, glossary, troubleshooting (Ch 2).

**Release notes** — rich-context companion to a changelog (what/when/why) (Ch 2).

**Sandbox** — environment to safely try sample code before implementing (Ch 5).

**Sequence** — linear content structure, one page after another (Ch 10).

**Structural quality** — how well a doc is written (the 3 Cs) (Ch 9).

**Swimlane diagram** — process diagram with one lane per actor (Ch 6).

**Template** — stable doc with placeholders for a repeated pattern (Ch 3).

**Time to Hello World (TTHW)** — time for a new dev to get a basic example working; adoption-ease metric (Ch 9).

**Toil** — manual, repetitive, automatable work that scales linearly; target of automation (Ch 11).

**Triage** — sorting/prioritizing feedback: valid? fixable? how important? (Ch 8).

**Tutorial** — procedural content for *learning* in a safe environment (Ch 2).

**Use case** — a set of tasks to complete a goal; drives content choices (Ch 2).

**User council** — small group of critical users giving ongoing feedback (Ch 8).

**User impact analysis** — short per-change research: who's affected, what docs change (Ch 11).

**User journey map** — timeline diagram of a user's path across channels (Ch 1).

**User persona** — semi-fictional character representing target readers (Ch 1).

**User story** — `As a [user], I want [activity] so that I can [goal]` (Ch 1).

**Web (structure)** — interconnected non-hierarchical pages, each linking to others (Ch 10).
