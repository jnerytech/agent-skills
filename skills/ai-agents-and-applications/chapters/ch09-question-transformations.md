# Chapter 9: Question transformations

## Core Idea
Low-quality RAG retrieval often stems from the user's question itself (poorly phrased, too narrow, or bundling multiple implicit questions), not from missing content — so transform the question before it hits the vector store, while keeping the original question for answer synthesis.

## Frameworks Introduced
- **Rewrite-Retrieve-Read**: an LLM rewrites the raw user question into a clearer, search-optimized query before retrieval; the original question is preserved for the final answer-synthesis prompt.
  - When to use: the question is poorly worded, vague, or verbose relative to how the vector store's content is phrased.
  - How: prompt an LLM with the question, ask for a revised query suited to semantic search; pipe `rewriter_prompt | llm | StrOutputParser()`; feed the rewritten string into `retriever` for `context`, but pass the untouched `RunnablePassthrough()` question into the final RAG prompt.
- **Multiple query generation (multi-query retrieval)**: an LLM decomposes one well-formed question containing several implicit sub-questions into 3-5 explicit, independently retrievable questions, each queried against the vector store, with results merged.
  - When to use: the question is well-formed but broad/compound (e.g., "Is LA warmer than Miami in April?" implies separate LA-temp and Miami-temp lookups).
  - How: custom — prompt for N alternative phrasings, parse with a `LineListOutputParser` into a `List[str]`, wrap a base retriever in LangChain's `MultiQueryRetriever(retriever=..., llm_chain=...)`. Standard — `MultiQueryRetriever.from_llm(retriever=basic_retriever, llm=llm)` does prompt+parse+multi-retrieve+dedupe internally.
- **Step-back prompting**: generate a broader, less specific version of a detailed question, retrieve context for both, and combine detailed context + abstract context + original question in one synthesis prompt.
  - When to use: the question is highly detailed and document chunks are fine-grained, so direct retrieval misses broader context the LLM needs for a complete answer.
  - How: prompt an LLM to produce a "step-back question" from the detailed one; retrieve `C_A` (abstract context) from that step-back question and combine with the original detailed question `Q_D` (and optionally its own detailed context `C_D`) in the final RAG prompt.
- **Hypothetical Document Embeddings (HyDE)**: have the LLM write a hypothetical answer/document for the user's question, then use that generated text — not the user's question — as the retrieval query.
  - When to use: the user's question is conceptually/phrasing-wise distant from how the answer is actually written in the document store, so direct question-to-chunk embedding similarity is weak.
  - How: prompt "write one sentence that could answer the provided question"; pipe the hypothetical sentence into the retriever for `context`, keep the real question for synthesis.
- **Query decomposition (single-step and multi-step)**: break a complex question into sub-questions, either independent (single-step, same as multi-query — run in parallel) or interdependent (multi-step — each sub-question's parameter is filled from the previous sub-answer, run sequentially).
  - When to use: single-step for independent sub-questions; multi-step for a question requiring a sequential chain of lookups (e.g., "average August temperature at the most popular sandy beach in Cornwall" needs beach-name → temperatures → average, in that order).
  - How: prompt the LLM to output a JSON list of `{Question, Parameter}` steps; execute each step against the data source, substituting the previous step's answer into the parameter; feed the accumulated answers into a final synthesis call. No dedicated LangChain class exists for this (unlike `MultiQueryRetriever`); LlamaIndex's `MultiStepQueryEngine` is cited as an inspiration.

## Key Concepts
- **Rewriter chain**: `rewriter_prompt | llm | StrOutputParser()` — an LCEL chain whose only job is turning a raw question into an optimized vector-store query string.
- **LineListOutputParser**: a custom `BaseOutputParser[List[str]]` that splits an LLM's newline-separated output into a list of non-empty question strings, needed because `StrOutputParser` only returns one string.
- **MultiQueryRetriever**: LangChain retriever class combining a prompt, an LLM, and a base retriever; internally generates multiple query variants, retrieves for each, and merges/deduplicates the documents into one result set.
- **Detailed context (C_D) / abstract context (C_A)**: in step-back prompting, C_D is retrieved with the original detailed question, C_A is retrieved with the generated broader question; both are combined in the final prompt.
- **Hypothetical document**: a fabricated short answer generated by the LLM purely to serve as a retrieval query — never shown to the user, never fact-checked, only used because its embedding lands closer to real document chunks than the bare question would.
- **Parameterized question sequence**: the JSON list of `{Question, Parameter}` steps produced for multi-step decomposition, where each `Parameter` is filled from the prior step's answer before execution.
- **Reciprocal Rank Fusion (RRF)**: scores documents by summing `1 / (rank + k)` (k typically 60) across multiple ranked result lists, so documents ranked highly by more than one query variant score higher; used to merge multi-query retrieval results.
- **Coarse-to-fine retrieval**: an alternative (from ch. 7/8) that changes the document chunks themselves rather than the question — search coarse summaries first, then re-search fine-grained chunks within the matched sections.

## Mental Models
- **Fix the question, not just the index**: after chapter 8's indexing improvements, chapter 9 treats the user's question as a second lever — most retrieval quality problems are "garbage query in, garbage context out," independent of how good the vector store is.
- **Preserve-original-for-synthesis pattern**: every technique in this chapter (rewrite, step-back, HyDE) transforms the question only for the retrieval side of the chain; the RAG prompt's `question` field always stays bound to `RunnablePassthrough()` on the untouched original question, since the transformed version (rewritten query, step-back question, hypothetical document) is often not itself a natural answer target.
- **Independent vs. interdependent decomposition**: the same "break the question into pieces" instinct forks into two different execution models — parallel/independent (multi-query, single-step decomposition) when sub-questions don't depend on each other, versus sequential/interdependent (multi-step decomposition) when each sub-answer feeds the next sub-question's parameter.
- **Semantic-distance repair, not literal correction**: rewrite, step-back, and HyDE all address the same root problem (question embedding sits far from the answer embedding) via three different repair directions — sharpen the query (rewrite), broaden it (step-back), or replace it with a fabricated answer-shaped text (HyDE) — rather than correcting grammar/spelling.

## Anti-patterns
- **Sending an ambiguous or overly complex question straight to the vector store**: vector search matches semantic similarity, not logical precision, so vague ("fun things to do") or compound ("is LA warmer than Miami in April") questions retrieve narrow or off-target chunks even when the right content exists in the store.
- **Using a single rewritten query for a question that's actually multiple implicit questions**: Rewrite-Retrieve-Read assumes the original question is just poorly phrased; if it's well-formed but compound, rewriting it into one improved query still under-retrieves — multi-query generation or decomposition is needed instead.
- **Applying single-step (parallel) decomposition to interdependent sub-questions**: a question like "average August temperature at the most popular sandy beach in Cornwall" cannot be split into independent parallel queries — the beach name must be resolved before the temperature query can run, requiring multi-step (sequential, parameterized) decomposition.
- **Letting HyDE's hypothetical document leak into the final answer path**: the hypothetical document is only a retrieval aid, not verified fact — using it (instead of the real question) as the `question` in the RAG synthesis prompt would let the LLM's own fabrication influence the "final" answer.

## Code Examples
```python
rewriter_prompt_template = """
Generate search query for the ChromaDB vector store from a user question,
allowing for a more accurate response through semantic search.
Just return the revised ChromaDB query, with quotes around it.
User question: {user_question}
Revised ChromaDB query:
"""
rewriter_prompt = ChatPromptTemplate.from_template(rewriter_prompt_template)
rewriter_chain = rewriter_prompt | llm | StrOutputParser()

retriever = uk_granular_collection.as_retriever()
rag_prompt_template = """
Given a question and some context, answer the question.
If you do not know the answer, just say I do not know.
Context: {context}
Question: {question}
"""
rag_prompt = ChatPromptTemplate.from_template(rag_prompt_template)
rewrite_retrieve_read_rag_chain = (
    {
        "context": {"user_question": RunnablePassthrough()} | rewriter_chain | retriever,
        "question": RunnablePassthrough(),
    }
    | rag_prompt
    | llm
    | StrOutputParser()
)
```
- **What it demonstrates**: the full Rewrite-Retrieve-Read chain — the rewritten query feeds retrieval, while the original question flows unchanged into synthesis.

```python
class LineListOutputParser(BaseOutputParser[List[str]]):
    """Parse out a question from each output line."""
    def parse(self, text: str) -> List[str]:
        lines = text.strip().split("\n")
        return list(filter(None, lines))

questions_parser = LineListOutputParser()
multi_query_gen_chain = multi_query_gen_prompt | llm | questions_parser

basic_retriever = uk_granular_collection.as_retriever()
multi_query_retriever = MultiQueryRetriever(
    retriever=basic_retriever,
    llm_chain=multi_query_gen_chain,
    parser_key="lines"
)

std_multi_query_retriever = MultiQueryRetriever.from_llm(
    retriever=basic_retriever, llm=llm
)
```
- **What it demonstrates**: both the custom multi-query retriever (explicit parser + chain) and the standard `MultiQueryRetriever.from_llm` shortcut.

```python
hyde_prompt_template = """
Write one sentence that could answer the provided question.
Do not add anything else.
Question: {question}
Sentence:
"""
hyde_prompt = ChatPromptTemplate.from_template(hyde_prompt_template)
hyde_chain = hyde_prompt | llm | StrOutputParser()

hyde_rag_chain = (
    {
        "context": {"question": RunnablePassthrough()} | hyde_chain | retriever,
        "question": RunnablePassthrough(),
    }
    | rag_prompt
    | llm
    | StrOutputParser()
)
```
- **What it demonstrates**: HyDE integrated into a RAG chain — the generated hypothetical sentence drives retrieval, the real question drives synthesis.

## Reference Tables
| Technique | Transforms question into | Retrieval calls | Best when |
|---|---|---|---|
| Rewrite-Retrieve-Read | one clearer/sharper search query | 1 | Original question is poorly phrased/vague |
| Multi-query generation | 3-5 alternative phrasings | N (merged via RRF) | Question is well-formed but has multiple implicit angles |
| Step-back prompting | one broader/abstract question | 2 (detailed + abstract) | Question is too narrow/detailed, missing higher-level context |
| HyDE | a fabricated hypothetical answer document | 1 | Question phrasing is semantically distant from document phrasing |
| Query decomposition (single/multi-step) | independent or sequential sub-questions | N (parallel or chained) | Question bundles independent or interdependent sub-questions |

## Worked Example
Step-back question generation integrated into a RAG chain (section 9.3), using the UK-tourism Chroma collection from earlier in the chapter:

1. **Prompt setup**: `llm = ChatOpenAI(model="gpt-5", ...)` (chosen over nano/mini because it generates more coherent abstractions); `step_back_prompt_template` asks: "Generate a less specific question (aka Step-back question) for the following detailed question, so that a wider context can be retrieved. Detailed question: {detailed_question} Step-back question:".
2. **Chain**: `step_back_question_gen_chain = step_back_prompt | llm | StrOutputParser()`.
3. **Test**: `user_question = "Can you give me some tips for a trip to Brighton?"` → `step_back_question_gen_chain.invoke(user_question)` returns `'What are some general tips for planning a successful trip to a coastal city?'`.
4. **Full RAG chain** (Listing 9.3): 
   ```python
   retriever = uk_granular_collection.as_retriever()
   step_back_question_rag_chain = (
       {
           "context": {"detailed_question": RunnablePassthrough()} | step_back_question_gen_chain | retriever,
           "question": RunnablePassthrough(),
       }
       | rag_prompt
       | llm
       | StrOutputParser()
   )
   ```
5. **Run**: `answer = step_back_question_rag_chain.invoke(user_question)` — context is retrieved using the broader step-back question ("coastal city" tips), but the synthesis prompt still answers the original specific Brighton question, producing a numbered list covering safety, beaches, lifeguard season, emergency contacts (999/Coastguard), and cultural areas (The Lanes, North Laine) — content a narrow "Brighton trip tips" query alone might have missed.

## Key Takeaways
1. When retrieval quality is poor despite good indexing, suspect the question's phrasing before re-engineering the vector store — question transformation is a second, independent lever from chapter 8's indexing work.
2. Use Rewrite-Retrieve-Read for single poorly-phrased questions; always keep the original question bound to the synthesis prompt's `question` field via `RunnablePassthrough()`, even though the rewritten/step-back/hypothetical text drives retrieval.
3. Reach for multi-query generation (custom `LineListOutputParser` chain or `MultiQueryRetriever.from_llm`) when a well-formed question implicitly bundles several angles; merge results with Reciprocal Rank Fusion.
4. Use step-back prompting when chunks are fine-grained and the question is too narrow to pull in needed background — combine abstract and detailed contexts in one final prompt.
5. Use HyDE when question phrasing is conceptually far from document phrasing — a fabricated hypothetical answer often embeds closer to real chunks than the bare question does.
6. Distinguish single-step decomposition (independent sub-questions, parallel execution) from multi-step decomposition (interdependent sub-questions, sequential execution with parameter substitution from prior answers); LangChain has no dedicated multi-step class — look to LlamaIndex's `MultiStepQueryEngine` for inspiration.
7. Test multiple techniques against your specific dataset rather than picking one universally: `MultiQueryRetriever` suits ambiguous questions, HyDE excels when query and document phrasing diverge conceptually.
