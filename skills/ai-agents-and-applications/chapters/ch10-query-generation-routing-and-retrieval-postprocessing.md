# Chapter 10: Query generation, routing, and retrieval postprocessing

## Core Idea
Beyond a single vector store, RAG systems must translate natural-language questions into the right query language for each backend (vector metadata filters, SQL, semantic SQL, Cypher/SPARQL), route each question to the correct data source with an LLM classifier, and postprocess retrieved chunks before synthesis to keep only the most relevant content.

## Frameworks Introduced
- **Self-querying (metadata query enrichment)**: transform a user question into a combined query with a metadata filter (sparse/keyword) plus a semantic search component.
  - When to use: chunks are tagged with metadata (destination, region, source, timestamp) and users ask questions that implicitly narrow scope (e.g., "festivals in Newquay" implies destination=Newquay).
  - How: (1) ingest chunks with metadata attached; (2) infer filters via `SelfQueryRetriever.from_llm(llm, vectorstore, question, metadata_field_info)`, or (3) build a custom structured LLM function call (Pydantic model) that separates `content_search` from filter fields, then translate it into the vector store's native filter syntax (e.g., `ChromaTranslator`).
- **Text-to-SQL (structured SQL query generation)**: LLM converts a natural-language question into an executable SQL query against a relational database.
  - When to use: data is structured/transactional (bookings, offers, customers) and needs exact filtering, joins, or aggregation.
  - How: use `create_sql_query_chain(llm, db)` against a `SQLDatabase` connection; feed the LLM the table schema plus sample rows (few-shot) to reduce hallucinated table/column names; pipe the raw output through a second "cleanup" LLM chain to strip markdown fences before executing with `QuerySQLDataBaseTool`.
- **Semantic SQL query (SQL similarity search)**: extend relational databases with vector columns (e.g., pgvector) so SQL queries can rank by embedding distance instead of exact match.
  - When to use: SQL `=`/`LIKE` is too rigid (misses "Robert" for "Roberto") and you want meaning-based ranking within a relational schema, optionally combined with exact filters/joins.
  - How: add a `VECTOR` column, populate it with embeddings (in-database function or external LangChain `OpenAIEmbeddings`), then `ORDER BY column <-> embedded_query` instead of `WHERE column = value`.
- **Graph database query generation (KG-RAG)**: LLM generates Cypher/SPARQL from natural language, executes it against a knowledge graph, and converts results back to natural language.
  - When to use: data is relationship-heavy (entities and edges) and requires multi-hop reasoning, inference, or explainability beyond similarity search.
  - How: craft a few-shot prompt template containing the graph schema and example Cypher queries, generate the query with a high-accuracy LLM (e.g., GPT-5), execute against Neo4j/Amazon Neptune, then synthesize the natural-language answer with a cheaper LLM (e.g., GPT-5-nano) fed the question, query, and results.
- **Chain routing (query router)**: an LLM classifies each incoming question and routes it to the retriever chain matching its intent (vector store, SQL DB, graph DB, etc.).
  - When to use: the application spans multiple content stores and a single retrieval path can't serve all question types.
  - How: define a structured output schema (`Literal["tourist_info_store", "uk_booking_db"]`) with a system prompt describing each data source; call `llm.with_structured_output(RouteQuery)`; map the returned `datasource` value to a dict of retriever chains and invoke the selected one.
- **Retrieval postprocessing**: filter/rerank retrieved chunks before sending them to the LLM to cut noise and improve answer quality.
  - When to use: after any retrieval step, before final synthesis.
  - How: apply a similarity-score threshold retriever, a keyword include/exclude filter, time-decay reweighting (`TimeWeightedVectorStoreRetriever`), or Reciprocal Rank Fusion (RRF) across multiple query variants.

## Key Concepts
- **Self-querying**: automatically inferring a metadata filter from a user's question rather than requiring explicit UI filters.
- **Dense vs. sparse retrieval**: dense uses embedding-distance similarity; sparse (BM25/TF-IDF) uses token-level inverted-index matching and supports Boolean logic and explainability.
- **Text-to-SQL**: LLM-generated SQL from natural language; accuracy improves with few-shot schema + sample-row prompts (per Rajkumar et al.).
- **Semantic SQL search**: similarity search inside a relational database via vector-type columns (e.g., pgvector), ordering by distance operator instead of equality.
- **KG-RAG (Knowledge Graph RAG)**: RAG variant where a graph database (nodes/edges, RDF triples, or proprietary formats) is queried via Cypher/SPARQL generated by an LLM.
- **Query router**: an LLM-based classifier that maps a question to the correct downstream retriever/data source.
- **Retrieval postprocessing**: the filtering/reranking stage applied to retrieved chunks before they're passed to the LLM for synthesis.
- **Reciprocal Rank Fusion (RRF)**: a reranking formula, `score = 1 / (rank + k)`, that merges ranked result lists from multiple queries into one fused ranking.
- **Time weighting**: adjusting similarity scores by recency using a decay factor so newer content ranks higher.

## Mental Models
- **Match the query language to the store, not the other way around**: every content store (vector, SQL, semantic SQL, graph) has its own native query language; the LLM's job is translation, not forcing one universal query format.
- **Router as a lightweight classification chain**: treat routing as a structured-output classification problem — describe each destination clearly in the system prompt and let the LLM pick a literal label, exactly like tool selection.
- **Retrieve broad, then narrow**: generate/retrieve more than you need (multiple queries, larger k), then use postprocessing (threshold, keyword filter, RRF) to compress down to only the most relevant chunks before synthesis.
- **Few-shot grounding reduces hallucination**: for both text-to-SQL and text-to-Cypher, supplying schema + example rows/queries in the prompt is the primary lever against wrong table/column/relationship names.

## Anti-patterns
- **Sending raw LLM SQL output straight to the database**: LangChain's `create_sql_query_chain` output often contains markdown fences (```sql ... ```) that break execution — always clean/strip before running.
- **Relying on exact-match SQL for fuzzy intent**: `WHERE first_name = 'Roberto'` misses "Robert," "Rob," "Bobby," etc.; use `LIKE` for partial matches or semantic SQL (embeddings) for meaning-based matches.
- **Using a single retriever for a multi-source application**: forcing all questions through one vector store or one SQL DB degrades accuracy when the right answer lives in a different backend — route instead.
- **Skipping schema/sample-row context in text-to-SQL prompts**: increases hallucinated table and column names; always include `CREATE TABLE` plus example rows.
- **No postprocessing before synthesis**: passing all raw retrieved chunks (regardless of relevance/score) to the LLM adds noise and increases the chance of low-quality or unfocused answers.

```python
class RouteQuery(BaseModel):
    """Route a user question to the most relevant datasource."""
    datasource: Literal["tourist_info_store", "uk_booking_db"] = Field(
        ...,
        description="""Given a user question, route it either to a tourist
        info vector store or a UK accommodation booking relational database.""",
    )

llm = ChatOpenAI(openai_api_key=OPENAI_API_KEY, model="gpt-5-nano")
structured_llm_router = llm.with_structured_output(RouteQuery)
system = """You are an expert at routing a user question to a tourist info
vector store or to an UK accommodation booking relational database. ..."""
route_prompt = ChatPromptTemplate.from_messages(
    [("system", system), ("human", "{question}")]
)
question_router = route_prompt | structured_llm_router

retriever_chains = {
    'tourist_info_store': tourist_info_retriever_chain,
    'uk_booking_db': uk_accommodation_retriever_chain
}
def retriever_chooser(question):
    selected_data_source = question_router.invoke({"question": question})
    return retriever_chains[selected_data_source.datasource]
```
- **What it demonstrates**: setting up an LLM-based query router with structured output and mapping the classification result to the matching retriever chain.

```python
def reciprocal_rank_fusion(results_groups: list[list], k=60):
    indexed_results = {}
    for group_id, results_group in enumerate(results_groups):
        for local_rank, doc in enumerate(results_group):
            indexed_results[(group_id, local_rank)] = doc
    fused_scores = {}
    for key, doc in indexed_results.items():
        group_id, local_rank = key
        if key not in fused_scores:
            fused_scores[key] = 0
        fused_scores[key] += 1 / (local_rank + k)
    reranked_results = [
        (indexed_results[key], score)
        for key, score in sorted(fused_scores.items(), key=lambda x: x[1], reverse=True)
    ]
    return reranked_results
```
- **What it demonstrates**: the RRF reranking algorithm used to merge results from multiple generated query variants (RAG fusion).

## Reference Tables
| Target store | Query mechanism | Match type | Best for |
|---|---|---|---|
| Vector store (metadata-enriched) | Self-querying / structured LLM function call → native filter (e.g., Chroma filter) | Sparse metadata filter + dense semantic search | Unstructured text with tags (destination, region, source) |
| Relational (SQL) database | Text-to-SQL (`create_sql_query_chain`) | Exact match / joins / aggregation | Structured, transactional facts (bookings, offers) |
| Relational + pgvector | Semantic SQL (`ORDER BY col <-> embedding`) | Embedding distance within SQL | Fuzzy/meaning-based matches on relational columns |
| Graph database (Neo4j, Neptune) | Text-to-Cypher / text-to-SPARQL | Graph traversal, multi-hop relationships | Entity-relationship reasoning, explainable inference |

## Worked Example
Goal: answer "Give me some offers for Cardiff, including the accommodation name" by generating and executing SQL against the `UkBooking` SQLite database.

1. Connect: `db = SQLDatabase.from_uri("sqlite:///UkBooking.db")`, confirm tables with `db.get_usable_table_names()` → `['Accommodation', 'AccommodationType', 'Booking', 'Customer', 'Destination', 'Offer']`.
2. Generate raw SQL: `sql_query_gen_chain = create_sql_query_chain(llm, db)`; `response = sql_query_gen_chain.invoke({"question": "Give me some offers for Cardiff, including the hotel name"})` produces a query wrapped in markdown fences (` ```sql ... ``` `), which fails if run directly (`sqlite3.OperationalError`).
3. Clean the SQL: pipe the raw response through a dedicated cleanup prompt/chain (`clean_sql_prompt | llm`) instructing the LLM to strip prefixes/suffixes and return only an executable, semicolon-terminated statement — yielding `SELECT Offer.OfferDescription, Offer.DiscountRate, Accommodation.Name FROM Offer JOIN Accommodation ON ... WHERE Destination.Name = 'Cardiff' LIMIT 5;`.
4. Execute: combine generation + cleanup + execution into `sql_query_gen_and_exec_chain = full_sql_gen_chain | QuerySQLDataBaseTool(db=db) | StrOutputParser()`, then `.invoke({"question": question})`.
5. Result: `"[('Early Bird Discount', 0.2, 'Cardiff Camping')]"` — ready to feed into a RAG synthesis prompt alongside the original question to produce a natural-language answer ("One offer for Cardiff is the 'Early Bird Discount' at Cardiff Camping, which provides a 20% discount.").

## Key Takeaways
1. Every content store needs its own query-generation path: metadata-enriched vector filters, text-to-SQL, semantic SQL (pgvector), or text-to-Cypher/SPARQL — pick based on data shape (unstructured tagged text, transactional records, or relationship graphs).
2. Text-to-SQL accuracy improves substantially with few-shot prompts that include the `CREATE TABLE` schema and sample rows; still clean LLM output (strip markdown fences) before execution.
3. Semantic SQL (via pgvector-style `VECTOR` columns and distance operators) bridges exact-match SQL and meaning-based retrieval, and can combine with traditional filters/joins for nuanced multi-table queries.
4. Use an LLM-based query router (structured output classification) to direct each question to the right retriever chain when an application spans multiple data sources.
5. Retrieval postprocessing (similarity threshold, keyword filters, time weighting, RRF) is a distinct, necessary stage between retrieval and synthesis — it trims noise so the LLM sees only high-quality context.
6. RRF (`1/(rank+k)`) is the standard way to merge multiple ranked result lists (e.g., from multi-query generation) into one fused, reranked set for RAG fusion.
7. Graph databases (KG-RAG) trade the simplicity of vector similarity for explainable, multi-hop relationship reasoning, generated via few-shot Cypher/SPARQL prompts with a high-accuracy LLM.
