# Chapter 4: Automated Testing

## Core Idea
Tests exist to give every party — developers, QA, management, clients — confidence to change a brownfield code base without fear; the practical move is to write a failing test that captures intended behavior *before* fixing a bug or changing code, then make it pass. You retrofit testing incrementally (never a 3-month halt), driven by the pain points and bugs you actually encounter.

## Frameworks Introduced

- **Write a test before fixing a bug**: capture the defect as an executable expectation first.
  - When to use: any time you're tasked with fixing a defect in a brownfield system.
  - How: narrow down where the bug lives, then write a test for what the code *should* do (not what it does). It fails — that's correct. Fix the code until it passes. The test stays as regression protection.
  - Why it works / failure mode: closes the feedback loop and prevents the bug recurring ("fixed once and only once"). Failure mode: code is so untestable you'd have to refactor first — if you lack tests to verify that refactoring, *hesitate*; do the best verification you can rather than introduce new risk.

- **Re-integrating an existing test project**: salvage inherited, stale test projects.
  - When to use: the brownfield app already has a test project that's incomplete, ignored, or won't compile.
  - How: (1) get it compiling *in isolation* in a separate solution (don't destabilize the team's CI); (2) for each invalid test choose Delete / Refactor / Ignore; (3) add project back to the solution; (4) watch for friction when developers pull latest — if the build breaks or friction appears, pull the project back out, fix, re-add; (5) separate unit from integration tests; (6) wire test execution into the build script.
  - Why it works / failure mode: gives vetted, passing tests inside CI. Failure mode: leaving friction in place long enough that developers invent harmful workarounds.

- **Three things to do with an invalid test**: Delete (no longer technically appropriate — version control keeps history), Refactor (still relevant — but usually faster to delete and rewrite), Ignore (still has business value but currently failing — use the framework's ignore attribute, *temporarily*).
  - When to use: triaging each inherited test.
  - Why it works / failure mode: Ignored tests rot like apples in a box — 1 becomes 2 becomes 15. Don't ignore for long.

- **Test-After Development (TAD) vs Test-Driven Design (TDD)**: two ways to test new code.
  - When to use: writing genuinely new code (the "greenfield oasis").
  - How: TAD writes tests after the code (intuitive, most popular). TDD writes tests first as a *design* activity — design expressed in the medium of test code, tests are a valuable side effect. Authors endorse evaluating TDD on a small scale.

## Key Concepts
- **Unit**: the smallest piece of code that can be tested; defining it is the hard part (e.g. "account created" could mean DB insert, service call, or retrieval).
- **State-based test**: verifies the state of an object/property/variable before and after an action; a "black box" test — no knowledge of internal workings.
- **Interaction-based test**: verifies how two or more objects interact (e.g. that `OrderService.Load` calls `FetchById` on its repository); knows *how* the code works.
- **Mock / fake object**: a proxy standing in for a real implementation. Mocks are auto-generated by a framework (RhinoMocks) with expectations; fakes can be hand-rolled (e.g. `FakeOrderRepository`).
- **Specification-based test (specifications)**: behavior described in natural language, flowing from user stories using "As a / I can / So that" syntax; best for *new* code, not retrofitting.
- **Integration test**: tests more than one unit at once, "subcutaneous" — from the database up to but not including the UI; slower because it hits real external resources.
- **Closing the feedback loop**: tests speed up bug discovery; every step a bug travels from the developer increases repair cost.
- **Incorrect test**: gives the illusion of validation but provides no meaningful verification — a false sense of security.
- **Friction**: anything that slows or annoys developers; remove it before they invent a workaround.

## Mental Models
- Use **state-based tests** when you only care about inputs and outputs and want each execution path verified independently with manageable setup.
- Use **interaction-based tests with mocks** when you need to verify how a unit collaborates with its dependencies — but only once you have clearly defined seams and logical layers (Ch 8); without them, interaction testing is near-impossible.
- Use **integration tests** when you must prove the real end-to-end path works (DB connection, permissions, config files) — they're often *easier* to add to brownfield apps than unit tests because the convoluted internals don't matter at the higher test level.
- Use **specifications** for outlining behavior not yet written; use state/interaction tests to verify correctness of existing code.

## Anti-patterns
- **Testing multiple units in one test**: more execution paths → more permutations → more configuration → brittle tests. Test each path separately, then a single test for interaction.
- **Tests that don't set meaningful expectations**: e.g. asserting only `Is.Not.Null` — passes against a near-empty stub implementation, giving false confidence.
- **Tests that don't reflect business requirements**: protect dead code, inflate coverage stats; delete them (and the dead code) when you stumble on them — don't hunt for them (low reward/effort).
- **Ignoring tests for too long**: ignored tests accumulate and rot.
- **Leaving friction in the workflow**: developers will adapt in detrimental ways (e.g. abandoning IIS for Cassini and breaking deploy assumptions).
- **Letting failing tests pass the build**: a failing test must be a stop condition, as serious as a compile error.
- **Sharing one database across developers/environments/CI**: integration tests mutate data; give each developer their own copy.

## Code Examples
```
[Test]
public void ImportMenuItemParser_Should_Transform_Input_Into_MenuItem()
{
    string sampleItem = "Item(Name:Chicken Vindaloo, Price:$11.95, Category:Entree)";
    IImportMenuItem menuItemParser = new ImportMenuItemParser();
    MenuItem menuItem = menuItemParser.For(sampleItem);
    Assert.That(menuItem.Name, Is.EqualTo("Chicken Vindaloo"));
    Assert.That(menuItem.Price, Is.EqualTo(11.95));
    Assert.That(menuItem.Category, Is.EqualTo("Entree"));
}
```
- **What it demonstrates**: rigid, meaningful expectations — the fixed version of a weak `Is.Not.Null` test; a near-empty `For()` returning `new MenuItem()` would now fail. Note the verbose, behavior-describing test name.

## Reference Tables

| Aspect | Unit test | Integration test |
|---|---|---|
| Scope | Single smallest unit | More than one unit; "subcutaneous" DB → below UI |
| External resources | Mocked/faked away | Real DB, files, web services |
| Speed | Fast | Much slower (open/use/close resources, no caching) |
| Brownfield difficulty | Hard — needs seams/layers | Easier — tests at a high level regardless of internals |
| When written | Before or after code | After code is complete |
| CI placement | Run always | Chain after unit tests; can run in a triggered second build |
| Physical location | `UnitTests` folder | `IntegrationTests` folder (same project is fine) |

## Worked Example
**Changing existing functionality, test-first.** A service formats a customer name as `FirstName LastName`; the client wants `LastName, FirstName`. There are no tests. Instead of editing the format string directly, write the test for the *desired* behavior:

```
[Test]
public void Display_name_should_show_last_name_comma_first_name()
{
    MyNameService sut = new MyNameService();
    Customer customer = new Customer("Tony", "Danza");
    string displayName = sut.GetDisplayNameFor(customer);
    Assert.That(displayName, Is.EqualTo("Danza, Tony"));
}
```

It fails against the current code — exactly as expected; there's no point verifying behavior you're about to delete. Now change the implementation's format string from `"{0} {1}"` to `"{1}, {0}"`, run the build, and the test passes. Commit code and test together. Outcome: the requested change *plus* confidence *plus* ongoing regression protection. (Reality check: most real code won't isolate this cleanly — a method that reads config, opens a DB connection, runs embedded SQL, and returns a DataSet needs significant layering refactoring first; that's Part II.)

## Key Takeaways
1. Confidence is the primary reason for tests; a large code base without tests is "a trapeze artist with no net" and breeds fear of change across the whole team.
2. Maintenance starts the instant a line is written — write a failing test before fixing a bug or changing code, so you know when you're done and the bug can't recur.
3. Don't halt development to retrofit tests; add tests opportunistically — no new code checked in without tests, every bug fix gets a test.
4. Distinguish state-based (black box, inputs/outputs) from interaction-based (collaboration, mocks) tests; prefer many small focused tests over one multi-unit test.
5. A passing test isn't a good test — assertions must set rigid, meaningful expectations, or they give false confidence.
6. Physically separate unit tests (fast) from integration tests (slow); let developers run fast tests often and chain slow ones separately in CI.
7. Make a failing test a build stop condition (`failonerror="true"`); code with failing tests ships nowhere. Each developer gets their own clean, auto-generated database for integration tests.
