# Glossary — Site Reliability Engineering (Google, 2016)

**50% cap** — Max share of SRE time on ops work (tickets, on-call, manual tasks); overflow goes back to dev (Ch 1, 5)
**Adaptive throttling** — Client rejects locally with probability max(0, (requests − K·accepts)/(requests+1)), K=2 (Ch 21)
**Admin Server** — RPC admin daemon with ACLs/audit logs that replaced ad-hoc SSH automation (Ch 7)
**Aggregate availability** — Successful requests / total requests; preferred over uptime for distributed services (Ch 3, 35)
**Alert / Ticket / Logging** — The only three valid monitoring outputs: act now, act in days, read later (Ch 1, 35)
**Alertmanager** — Routes, inhibits and deduplicates alerts by labelset (Ch 10)
**Auxon** — Intent-based capacity-planning tool built by SRE (Ch 18)
**Bad Apple Theory** — False belief that failures come from bad individuals (Ch 30)
**Bimodal latency** — Few hung requests consume all threads, causing errors for many (Ch 22)
**Bisection** — Split the system in half, find the faulty half, repeat (Ch 12)
**Black-box monitoring** — Testing externally visible behavior as a user sees it (Ch 6, 10)
**Blameless postmortem** — Incident write-up that finds contributing causes without indicting people (Ch 1, 15)
**Borg / Borgmon** — Google's cluster OS / its time-series monitoring (Prometheus analog) (Ch 2, 10)
**Break-glass** — Noisy, audited bypass of normal release gates (Ch 17)
**CAPA** — Corrective and Preventive Action; regulated-industry postmortem (Ch 33)
**Canary** — Small slice of production running a new version, watched before wider rollout (Ch 8, 17, 27)
**Cascading failure** — Failure that grows via positive feedback as healthy parts take over failed load (Ch 22)
**Change-/Process-/Test-induced emergency** — The three emergency archetypes (Ch 13)
**Chubby** — Paxos-based lock service (Ch 2, 23)
**Criticality** — Request priority (CRITICAL_PLUS, CRITICAL, SHEDDABLE_PLUS, SHEDDABLE) propagated with the request (Ch 21)
**Deadline propagation** — Downstream calls inherit the remaining absolute deadline (Ch 22)
**Defense in depth (data)** — Soft deletion → backups → early detection/validation, layered (Ch 26)
**Deterministic subsetting** — Clients take disjoint slices of shuffled backend lists so load spreads evenly (Ch 20)
**DiRT** — Disaster Recovery Testing; annual company-wide real-outage drills (Ch 11, 33)
**Distributed consensus** — Agreement among processes over an unreliable network (Paxos, Raft, Zab) (Ch 23)
**Early Engagement Model** — SRE involved from design phase rather than at handoff (Ch 32)
**Embedded SRE** — SRE temporarily joining an overloaded team to fix practices (Ch 30)
**Error budget** — 1 − SLO; the allowed unreliability spent on launches and risk (Ch 1, 3, 4)
**Escalator / Outalator** — Alert-escalation system / outage tracker aggregating alerts into incidents (Ch 16)
**Essential vs accidental complexity** — Inherent to the problem vs removable by engineering (Ch 9)
**Exactly-once (Workflow)** — Each work unit reflected in permanent state once (Ch 25)
**Exit criteria** — Explicit conditions for declaring an incident over (Ch 35)
**Fail closed (cron)** — Prefer skipping a launch to double-launching (Ch 24)
**Fail Sanely** — Reject implausible config; keep prior state and alert (Ch 35)
**Fault order (U)** — How a bug's impact scales with traffic; U = R·K / C from canary reports (Ch 17)
**Four golden signals** — Latency, traffic, errors, saturation (Ch 6)
**Freelancing** — Uncoordinated changes by individuals during an incident (Ch 14)
**GSLB** — Global Software Load Balancer: DNS, user-service and RPC levels (Ch 2)
**Graceful degradation** — Doing less work per request under load (Ch 22)
**Hermetic build** — Same inputs → identical output, independent of build machine (Ch 8)
**Hierarchy of automation classes** — From none → externally maintained → generic → internal → autonomous (Ch 7)
**Hypothetico-deductive method** — Iterate observe → hypothesize → test (Ch 12)
**Incident Command System (ICS)** — Role-based incident framework: IC, Ops, Communication, Planning (Ch 14)
**Incident Commander (IC)** — Holds high-level state and every undelegated role (Ch 14)
**Intent-based capacity planning** — Encode requirements ("why"), auto-generate allocation plan (Ch 18)
**Lame duck state** — Backend still serving but asking clients to go elsewhere (Ch 20)
**Launch Coordination Engineering (LCE)** — SRE consultants who audit and gate launches (Ch 27)
**Load shedding** — Dropping part of the traffic near overload (Ch 21, 22)
**MTTR / MTTF / MTBF** — Mean time to repair / to failure / between failures (Ch 1, 17)
**Multi-Paxos** — Paxos with stable leader; one round trip per decision (Ch 23)
**N + 2** — Capacity for peak with two largest instances down (one planned, one unplanned) (Ch 2, 18, 35)
**Negative result** — Experiment where expected effect is absent; conclusive, worth publishing (Ch 12)
**Nines** — Availability shorthand; each extra nine is 10× less downtime (Ch 3, 35)
**On-call 25% rule** — ≤25% of time on-call → ≥8 engineers single-site, 6 per site dual-site (Ch 11)
**Operational overload / underload** — Too much ops work vs too little production exposure (Ch 11, 30)
**Overloaded; don't retry** — Error that stops retry amplification up the stack (Ch 21)
**Polarizing time** — Each person fully on interrupts or fully on projects, never both (Ch 29)
**Postmortem trigger** — Predefined criterion requiring a postmortem (Ch 15)
**Production meeting** — Weekly SRE/dev meeting on outages, pages, changes, SLOs (Ch 31, 35)
**Production Readiness Review (PRR)** — Review required before SRE onboards a service (Ch 32)
**Progressive rollout** — Staged release by traffic fraction and region; roll back first (Ch 8, 27, 35)
**Query of death** — Request whose content crashes the server (Ch 22, 35)
**Replicated State Machine** — Same ops in same order on many replicas, ordered by consensus (Ch 23)
**Retry budget** — ≤3 attempts per request; retries <10% of client requests (Ch 21, 22)
**Service Reliability Hierarchy** — Monitoring → Incident Response → Postmortem → Testing → Capacity → Development → Product (Part III)
**SLI / SLO / SLA** — Indicator / target for the indicator / contract with consequences (Ch 4)
**Soft deletion** — Mark deleted, destroy after 15–60 days (Ch 26)
**Split-brain** — Two nodes both acting as leader (Ch 23)
**Sum of rates** — Rate per task, then aggregate; robust to counter resets (Ch 10)
**Symptoms vs causes** — What's broken (alert on this) vs why (Ch 6)
**Toil** — Manual, repetitive, automatable, tactical, no enduring value, O(n) with service growth (Ch 5)
**Virtue of boring** — Predictable systems are desirable; surprise is the enemy (Ch 9)
**Wheel of Misfortune** — Role-played disaster drill for on-callers (Ch 1, 15, 28)
**Workflow (Task Master)** — Google's MVC-style continuous pipeline system (Ch 25)
